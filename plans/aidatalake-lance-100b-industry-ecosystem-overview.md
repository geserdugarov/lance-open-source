# AI DataLake and Lance: industry, community, and ecosystem assessment at 100 billion vectors

**Focused comparison update:** See [Lance, Milvus, Qdrant, and PostgreSQL + pgvector at 100B](100b-vector-ecosystem-comparison.md) for the revised ecosystem assessment, confirmed full-corpus workload, and accompanying one-slide PowerPoint and HTML review. The broader industry and integration research below is retained as context.

**Research date:** 2026-11-06. **Confirmed workload:** approximately **100 billion 1,024-dimensional embedding vectors**. FP32 is the sizing assumption; precision, query concurrency, recall requirements, filter distribution, and media sizes remain unspecified. **Evidence:** official product documentation, tagged releases/source, and the local Aura design at checkout `ee7c527de`. No new performance experiments were run. Numbers below distinguish published measurements, product claims, calculations, and proposed acceptance criteria.

The decision brief is intended as approximately two pages; the appendices retain the supporting data and engineering detail.

## Decision brief

### 1. Industry position and work to prioritize

**AI DataLake should compete on the complete cost and reliability of mining a 100-billion-vector multimodal dataset:** ingestion, distributed index maintenance, filtered retrieval, large result extraction, and reproducible training. At this size, FP32 embeddings alone occupy **409.6 TB**; five-bit RaBitQ codes add **64 TB** before IDs and other overhead. A faster distance kernel is useful, but routing, data movement, index freshness, and recovery determine whether the system is practical.

Evaluate two workload profiles separately: concurrent top-10/100 application serving, and top-10,000/1,000,000 dataset mining. This assessment prioritizes the latter and its maintenance pipeline; small-k latency alone does not measure that use case.

Huawei positions Aura + Lance for 100-billion-scale collections, with top-k = 10,000 taking seconds and top-k = 1,000,000 taking minutes. These are **published product claims without enough configuration or recall data to reproduce them**. The local design separately targets 20 billion initial vectors and 4–5 billion incremental vectors/day; those are planning requirements, not demonstrated throughput. [Huawei scenario](https://support.huaweicloud.com/productdesc-aidatalake/aidatalake_08_0032.html); [local Aura design](aura-distributed-indexing.md).

| Comparator | What matters at 100 billion vectors | Implication for AI DataLake |
|---|---|---|
| **FAISS** | Algorithm library with CPU/GPU implementations and an on-disk, distributed 1.5-trillion-vector case study. It is a credible large-scale algorithm baseline, although that study used 144-dimensional byte vectors and range search. | Compare training, assignment, compression, and retrieval quality; Aura must supply catalog, scheduling, transactions, recovery, and multimodal workflows. [FAISS study](https://github.com/facebookresearch/faiss/wiki/Indexing-1T-vectors). |
| **Milvus 3.0** | Distributed retrieval now includes read-only external Lance collections, with its own indices and refresh lifecycle. Lake-resident data is already a competitive capability. | Differentiate through integrated data preparation/training and large-k economics; evaluate Milvus as both a serving competitor and an optional serving integration. Storage V3 must be enabled. [Storage V3](https://milvus.io/docs/storage-v3.md). |
| **LanceDB** | Embedded OSS provides the local database; Enterprise adds distributed execution and maintenance. Published distributed benchmarks reach 10 billion entries. | Reuse Lance algorithms; compare Aura against Enterprise for orchestration, cache placement, failure recovery, and total cost. Embedded OSS throughput is a different comparison. [Distributed architecture](https://www.lancedb.com/blog/how-lancedb-accelerates-vector-search-at-10-billion-scale). |

**The highest-value work is making scale behavior explicit.** Specify distributed query routing and global top-k separately from the existing build proposal. With 400–1,000 segments, returning one million candidates from every segment transfers **4.8–12 GB of IDs and scores** for a final answer of only 12 MB. Implement bounded candidate streams, global merging, and measured routing/pruning; dividing k evenly between segments can lose the true global neighbors. Maintain indices incrementally, bound segment growth and unindexed tails, and preserve completed work through retries. Extend existing compaction, FTS, and distributed indexing rather than treating them as missing features. [Existing Aura capabilities](https://support.huaweicloud.com/devg-aidatalake/aidatalake_05_0047.html); [distributed design boundaries](aura-distributed-indexing.md).

**There is no verified performance-parity conclusion for this exact workload.** The reviewed public evidence does not establish a comparable 100-billion × 1,024-dimensional result across all products. LanceDB's 10-billion results and FAISS's trillion-scale study justify architectural choices, not latency extrapolation. Benchmark at matched recall, hardware cost, filters, concurrency, cache state, and returned payload.

### 2. Released Lance capabilities worth productizing

Library versions and file-format versions are separate. Use stable file format **2.2** as the production baseline; **2.3 remains unstable**. A stable library release does not make every included feature mature at 100 billion rows. ### 3. Ecosystem gaps and investment order

AI DataLake 26.9 already lists **Aura 3.9.0, Ray 2.54.0, Spark 4.0.2, and Flink 1.20**. The gap is consistent Lance behavior across these engines. [Product release matrix](https://support.huaweicloud.com/verspt-bulletin-aidatalake/aidatalake_bulletin_0003.html).

Prioritize **P0: scale benchmarking, distributed query/maintenance contracts, and a certified engine/version matrix**. Follow with **P1: reliable Flink ingestion, shared catalog/credentials, and efficient Spark/Ray-to-training handoff**. Spark's released connector already supports distributed index maintenance, while the released Flink SQL sink is insert-only and its checkpoint implementation exposes a replay risk. Iceberg's checkpoint-coordinated commits and upserts provide a useful acceptance baseline. Defer **P2: additional SQL engines, native Ascend index kernels, and specialized late-interaction/deduplication features** until workload measurements justify them. Detailed evidence and acceptance criteria follow.

## Appendix A. Capacity and execution consequences

All sizes here are **calculated**, use decimal TB/GB, and assume one embedding per record. Index code sizes exclude IDs, centroids, factors, graph links, alignment, metadata, replicas, and retained versions. Quantized indices normally coexist with the original embedding column.

| Representation | Bytes/vector | Payload at 100 billion vectors | Interpretation |
|---|---:|---:|---|
| FP64 embedding | 8,192 | 819.2 TB | The local design mentions FP64 and FP32 inconsistently; settle the actual type. |
| **FP32 embedding** | **4,096** | **409.6 TB** | Sizing baseline: `100e9 × 1,024 × 4`. |
| FP16 embedding | 2,048 | 204.8 TB | Requires quality validation; not a free conversion. |
| SQ8 code | 1,024 | 102.4 TB | Code payload is 4× smaller than FP32. |
| RQ5 code | 640 | 64.0 TB | Code payload is 6.4× smaller than FP32. |
| RQ1 code | 128 | 12.8 TB | Code payload is 32× smaller; quality/refinement costs differ. |
| PQ128 / PQ256, 8-bit subcodes | 128 / 256 | 12.8 / 25.6 TB | Candidate compression configurations to compare with RQ5. |
| One 64-bit ID/vector | 8 | 0.8 TB | Additional lower-order storage, not the entire metadata cost. |

FP32 + RQ5 + one ID copy already totals **474.4 TB**, before media and the other overheads. A graph storing 64 four-byte neighbor references/vector would add **25.6 TB** for that adjacency array alone; this is an illustrative graph budget, not a measured Lance or Milvus index size. A second independently retained FP32 embedding model adds another 409.6 TB before its index. Avoid equating a 32× reduction in one-bit codes with a 32× reduction in the complete platform footprint.

**Build and ingestion.** A hypothetical complete 100-billion-vector build in 24 hours requires **1.157 million vectors/s**, at least **4.74 GB/s** of aggregate raw-vector input, and **0.741 GB/s** of RQ5 code output. These are one-pass I/O lower bounds; training, shuffle, retries, extra passes, and object requests add work. For the local design's conditional 4–5 billion/day growth scenario, the minimum average is **46,296–57,870 vectors/s**, or **16.384–20.480 TB/day** of FP32 embeddings. At five billion/day, 24 hours of unindexed data means a **20.48-TB tail**: queries must not quietly degrade into scanning it. Expose both write-to-visible and write-to-indexed lag.

**Physical segmentation.** Start experiments with 100–250 million vectors per index segment: **1,000–400 segments** at full scale, with **64–160 GB of RQ5 codes per segment**. These are sizing hypotheses, not recommended defaults or node counts. Segment placement must account for concurrent queries, memory overhead, NVMe capacity, and skew. Keep layout independent of the number of workers. The local design's shard-local models make build recovery practical, but also require a global routing strategy or substantial fan-out. Fragment, segment, IVF partition, and compute worker are different units. [Local indexing design](aura-distributed-indexing.md).

**Routing and skew.** With 1,000 segments, probing 20 IVF partitions in each segment visits **20,000 partitions**, not 20 overall. Compare selective routing against searching every segment at identical recall. Include near-duplicates, hot tenants, unequal shard sizes, cross-modal queries, and evolving embedding distributions. FAISS's trillion-scale case encountered inverted lists above 100 million entries despite an average near 150,000; its tail latency improved only after addressing this skew. [FAISS case study](https://github.com/facebookresearch/faiss/wiki/Indexing-1T-vectors).

**Large-k and payload delivery.** One million `(uint64 ID, float32 score)` pairs occupy **12 MB**, but their FP32 embeddings occupy **4.096 GB**. If each selected record also requires a 1-MB image, media delivery becomes **1 TB**. Report ID-only search latency, first-result latency, complete result-transfer time, and media/embedding hydration separately. Streaming or materializing a versioned selection table is often more useful than constructing a giant client-side result object. Exact full-vector reranking adds random reads; measure bytes fetched per returned neighbor.

**Object storage and cost.** Scanning 409.6 TB once takes approximately **11.4 hours at 10 GB/s**, **68.3 minutes at 100 GB/s**, or **6.83 minutes at 1 TB/s** of sustained aggregate throughput. These are idealized byte-transfer floors. Size OBS bandwidth and request rates from actual range sizes and cache misses; add network shuffle and write amplification. Track **cost per billion vectors built**, **cost per million successful queries at fixed recall**, and **cost per million usable training samples**. Include compute, object requests, storage, NVMe/cache, traffic, replicas, and retained versions; no defensible currency estimate is possible without deployment rates and workload duty cycle.

| Evidence | Published numbers and conditions | Relevance and limitation |
|---|---|---|

Different dimension, representation, search semantics, hardware, and quality evaluation. [Study](https://github.com/facebookresearch/faiss/wiki/Indexing-1T-vectors). |
| **LanceDB Enterprise**, April 2026 | **10 billion × 1,536 FP32 random vectors**, 10 segments on 10 query nodes, top-k = 100: **18/20/21 ms p50/p95/p99**. ## Appendix E. Proposed work packages and acceptance evidence

These are **recommended engineering gates**, not existing SLAs or measured results. P0 means prerequisite to a credible 100-billion-vector commitment; P1 completes high-value workflows; P2 follows demonstrated demand. Effort estimates need an implementation audit.

| Priority / work package | Reviewable deliverable | Proposed acceptance evidence |
|---|---|---|
| **P0 — Establish a reproducible 100B baseline** | Versioned benchmark suite and capacity/cost report, using real 1,024-dimensional embeddings. | Stages at **100M → 1B → 10B → 100B**; smaller stages debug the system, final capacity sign-off requires a full-size run. Test k = **10, 100, 10,000, 100,000, 1,000,000**, filter selectivity **100%, 10%, 1%, 0.1%**, and concurrency **1, 16, 64** for representative combinations. |
| **P0 — Global query execution** | Routing, distributed filters, candidate exchange, top-k merge, streaming/export, and memory-budget contract. | Provisional **recall@k ≥ 0.95**, with 0.99 sensitivity runs, against exhaustive reference results for a fixed query set. | **P0 — Incremental indexing and recovery** | Shared create/optimize pipeline with persistent assignments, model identity, bounded tasks, and atomic publication. | For the local five-billion/day scenario, sustain **≥58,000 indexed vectors/s over 24 hours** without a growing backlog. Record catch-up headroom rather than declaring average throughput sufficient. |
| **P0 — Cross-engine compatibility** | Matrix of runtime, bindings, connector, file version, table flags, and permitted maintenance operations. | Aura/Spark/Ray/Flink read the same pinned snapshot and agree on IDs, types, nulls, filters, and counts. Unsupported clients fail clearly. Cleanup preserves all protected data, indices, clones, and blobs. |
| **P1 — Streaming correctness** | Checkpoint-aware Flink sink, CDC contract, and freshness dashboard. | No duplicate or lost source IDs after failure between file write, Lance commit, and checkpoint completion; exercise restarts, rescaling, credential renewal, and schema changes.
